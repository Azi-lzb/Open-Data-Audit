# 版本管理（V3 组件编号与版本基线）

本目录是 **审核工具（产品代号 V3）** 的产品及组件版本登记与变更历史中心。
只存元数据、版本历史、组件关系与变更索引；**不得**存放源代码副本、
配置工作簿备份、运行输出、pytest temp 或编译产物——这里不是备份仓库。

## 编号体系

| 层级 | 编号 | 含义 |
|---|---|---|
| 产品 | `V3` | 产品身份 / 项目代号。**不是版本号**。 |
| 系统 | `S1` / `S2` / `S3` | 逐笔统计系统 / 报表采集系统 / 大集中统计系统 |
| 功能 | `Sx-Fxx` | 一个系统内的顶级业务功能（以当前 UI 顶级入口为准） |
| 配置 | `Sx-CFG-xx` | 一个系统的配置工作簿 |
| 产品发布版本 | `VYY.MAJOR.MINOR.PATCH` | 年份.大版本.中版本.小版本，窗口及各平台产物统一 |
| 组件版本 | `vMAJOR.MINOR.PATCH` | 每个功能/配置组件独立 |

禁止把 `3.0 / 3.1 / 3.2 / 3.3 / period_v2` 解释成产品或组件版本号——
它们只是历史文件编号 / 历史技术目录名，是否改名另行迁移。

## 权威索引与历史

- `VERSION_MANIFEST.json`：**当前组件版本的唯一权威清单**（产品 / 系统 /
  功能 / 配置 / 版本 / 实现路径 / 配置文件映射）。改版本先改它。
- 各组件目录内的 `CHANGELOG.md`：该组件自己的**纵向**版本历史。
- `GPT修改记录/`：一次修改任务的**横向**记录（多组件联动、根因、测试）。
- 两者不能互相替代：CHANGELOG 回答"这个组件经历了什么"，
  GPT修改记录 回答"那次任务做了什么"。

## 基线说明

全部 17 个组件（11 功能 + 6 配置）以 **v1.0.0** 为版本管理体系建立时的
基线。**不倒推历史 SemVer**：建立前的修改可通过 `GPT修改记录/`、Git
历史与旧文档回溯，但不伪造 v0.x / v2.x 等历史版本。

## 版本号规则（SemVer）

整包版本唯一读取 `VERSION_MANIFEST.json` 的 `product.version`，初始为
`26.1.0.0`，展示为 **审核工具 V26.1.0.0**。新增大的平台系统升级大版本，
现有系统新增功能升级中版本，修复缺陷和局部逻辑调整升级小版本；升级较高
一段时清零其后各段，每年首个大版本从 `YY.1.0.0` 开始。产品发布历史记录在
`产品发布/CHANGELOG.md`；不根据打包时间自动更改版本。

以下 SemVer 规则用于功能和配置组件，独立于整包版本。

- **PATCH** v1.4.2 → v1.4.3：Bug 修复、内部实现修复、性能优化、安全保护；
  不改变外部业务契约、不改变配置结构。
- **MINOR** v1.4.2 → v1.5.0：新增向后兼容功能 / 可选能力 / 规则能力 /
  兼容字段；原有业务仍可继续运行。
- **MAJOR** v1.x.x → v2.0.0：不兼容业务语义、配置结构重大变化、接口契约
  破坏性变化、输入输出协议重大变化。

## 功能版本与配置版本独立（铁律）

只改功能代码 → 只升该功能版本，相关配置版本不动；只改配置内容 → 只升
该配置版本，功能版本不动；两者都改 → 分别各自升级。禁止"功能升级了，
相关配置一起加版本"。

## 每次修改的固定流程

修改前：判断所属系统（S1/S2/S3）→ 识别受影响功能（Sx-Fxx）与配置
（Sx-CFG-xx）→ 读 `VERSION_MANIFEST.json` 确定修改前版本。
修改后：判断 PATCH/MINOR/MAJOR → 更新 `VERSION_MANIFEST.json` → 更新
受影响组件的 `CHANGELOG.md` → 新增 `GPT修改记录/`（含【组件版本】字段）
→ 最终报告列明"哪些组件从什么版本升到什么版本"。

详细规则见 `rules/11_版本管理与组件编号.md`。
