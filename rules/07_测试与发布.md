# 测试、验收与发布规则

测试范围以 `AGENTS.md` 的功能变更要求为入口；本文件规定验证层级和报告证据。

## 测试选择

- 每次新增/修改功能，先跑对应定向测试，再按 `core/tests/TEST_GROUPS.md` 跑受影响的 S1/S2/S3/S5 组；跨系统公共代码覆盖所有受影响组。新增测试模块必须登记到系统分组。
- 合入 `main` 前运行 core 全量 pytest。只改文档时不要求运行 pytest；只改 Python 时做编译检查。
- 按风险追加：真实业务数据、文件结构/reopen、Excel/WPS/LibreOffice 真机、VBA/黄金基线对拍。具体平台边界见 `rules/02` 和 `rules/03`。
- Office 路径不得只靠 mock 宣布通过；未执行的平台验收必须注明“未执行”。
- 读取项目现成配置的测试逐文件优先使用 `config-real/`，对应文件缺失时才回退 `config/`；默认配置快照保持相对目录独立选择。统一使用 `core/tests/config_paths.py`，真实配置只读，修改场景先复制到临时目录，并记录本次实际配置来源。

## 必要证据

- 业务输出：相同输入和配置下，核对文件数量、数据数量、关键值与审核结论；日志/性能开关不得改变业务结果。
- 原始文件：重要流程执行前后比较 SHA-256，证明输入未被修改。
- 工作簿：验证预期公式、格式和结构；Direct OOXML 结果需能重新打开。
- VBA/规则迁移：核对数量、启用规则存活率和触发行为；数量差异必须逐项解释，不能以“基本一致”代替。

## 报告格式

说明实际执行的命令/范围，并报告 `passed / skipped / failed / errors` 数量；列明新增或未新增测试的理由、真实数据验收结果及未执行的平台专属项目。不得把未执行写成通过。

## 性能优化

性能优化还要证明业务结果和文件结构未变。测量项以 `rules/09_技术实现参考.md` 的性能清单为准，至少保留输入规模、关键阶段耗时、输出差异和公式错误信息。

Rust 迁移必须分别测试读取、计算、写入；写入使用同一份预生成结果数据，记录数据传入 Rust 的开销，并在相同 ZIP 压缩条件与各自交付设置下分别比较耗时和文件大小。每完成一个系统，先通过系统组和真实样本对拍，再运行全项目 S1-S5 回归及 Windows/Linux AMD64 可用环境的验证，方可进入下一系统。Office 相关优化必须实际完成重算、保存和缓存验证，mock 不算公式兼容验收；未执行的平台或真机项目明确列为未执行。完整验收要求见 `rules/12_Rust优化与引擎路由.md`。
