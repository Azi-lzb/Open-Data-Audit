# Rust 优先选型、引擎路由与迁移验收

本规则与 [规则 13：表格读写技术选型与主动优化](13_表格读写技术选型与主动优化.md) 配合使用：13 定义输入输出契约、逐操作后端匹配、用户选择与开发维护主动检查；本文件保留 Rust 候选优先级、现行快路径、S5/S2/S3/S1 迁移顺序和完整验收要求。不得把通用库的能力描述当作本项目已适配/已验收的证明。

## 范围与原则

- 覆盖 S1/S2/S3/S5；S4 只有预览 UI，暂不实现或迁移。S5 近期已优化，先做基线和候选操作评估，不要求重写成熟路径；只有取得稳定、可感知的端到端收益才迁移。其后按 S2、S3、S1 分系统实施，每次完成一个系统验收再进入下一个。
- 新增的性能敏感解析、批量计算、读写能力优先评估 Rust；正确性、端到端实测与跨平台支持决定采用和默认路由，禁止假定 Rust 必然更快。
- XLSX 全表纯值读取按基准优先选择 Calamine 系 reader；已有 Direct OOXML 定点读取、条件规则读取和专用 writer 仍按各自能力保留，不因全表读取结果而泛化替换。迁移候选仍须从实际热点出发，不得为了“工具齐全”给已使用 Calamine 的读取操作增加 OpenPyXL 用户选项。
- Rust 源码、适配器和统一业务契约位于 `core/`；Python 可继续负责编排与外壳桥接。不得在两个 shell、历史副本中另建业务实现。
- 优先复用已有 Calamine、Direct OOXML 和 Office 能力，先测当前瓶颈，不能将现有优化重新包装为新成果。

## 按操作选择工具

- 读取值、读取 OOXML 结构、规则计算、新建工作簿、编辑已有工作簿、公式重算分别定义能力，不建立不分任务的“Rust、OOXML、openpyxl、Office”固定优先链。
- 本次审计的 Direct OOXML 是项目自有 Python 实现，不是一个通用引擎或单一固定库：reader 用 `zipfile` 读 ZIP 部件并以 `ElementTree.fromstring` 解析；`CellValueProvider` 首次读取时解析整张 sheet XML、建立稀疏坐标缓存，不是流式 reader，也不提供公式文本/合并区域。条件格式 reader 另有专用规则解析。S1/S5 writer 按行写 worksheet XML，但调用方的 `DataTable.rows` 已整体驻留内存且需预扫描样式；S2 writer 会先构造并保留三张表的完整 worksheet XML 字符串；S3 writer 则编辑并保留已有 OOXML 部件。Rust reader/writer 的基准路径是独立 Release CLI，Python 通过 JSON 和子进程调用，桥接不属于引擎内部耗时。公式文本与合并区域专项比较的是 Python-calamine 加 XML 元数据混合 reader 和 Rust calamine crate，两者在样例的 3 个公式和 2 个合并区域上相符；不得将这些能力归给 Direct 值 reader。依据：基准报告《范围与实现审计》《公式与合并区域专项》（`../../3.open-data-audit-benchmark/results/benchmark_report.md`）。
- XLSX 纯值全表读取默认优先 Calamine 系（Rust `calamine` crate，或经同一契约验收的 `python-calamine` 绑定）。基准中 Rust crate 读取 50,001×20 全表的中位耗时/峰值内存为 1.043 秒/73.7 MB，Direct OOXML 为 12.524 秒/770.1 MB；真实 S2 工作簿 729×16 全表为 0.012 秒/4.0 MB 与 0.210 秒/29.8 MB。两组纯值坐标/值摘要一致。全表读取证据不代表所有定点、元数据或条件规则读取都应切换；`python-calamine` 绑定的适配器仍须按目标平台和类型/空值契约单独验收。依据：基准报告《读取结果》《读取一致性》（`../../3.open-data-audit-benchmark/results/benchmark_report.md`）。
- Calamine 用于读取，不能承担写入。优先评估尚未使用 Calamine 且读取耗时显著的 OpenPyXL 路径；小型配置文件即使微基准更快，若绝对耗时收益可忽略，也不作为优先迁移项。保留日期、文字、数值、空白、错误、公式缓存和原始行列语义。
- 新建纯数据工作簿默认暂不从项目专用 Direct OOXML writer 切换到 `rust_xlsxwriter`。同压缩级别的基准显示 Rust 端到端耗时在不同规模下有收益，但收益随规模和压缩设置变化；30 万行×20列、ZIP level 1 时 Rust 为 16.631 秒，Direct 为 20.356 秒，而 Rust Python JSON 桥接路径峰值内存为 1,588.2 MB，Direct 为 376.6 MB（约 4.2 倍）。只有先消除桥接层数据复制/JSON 序列化开销，并复测确认内存符合该功能预算后，才重评新建写入默认路由。依据：基准报告《写入结果》《写入阶段耗时中位数》（`../../3.open-data-audit-benchmark/results/benchmark_report.md`）。
- `rust_xlsxwriter` 只新建工作簿，不支持原位编辑或保留既有模板部件。S2 三表结果构造器和 S3 模板原位编辑继续使用项目专用 Direct OOXML 实现，不得路由到 `rust_xlsxwriter`。依据：基准报告《范围与实现审计》《结论》（`../../3.open-data-audit-benchmark/results/benchmark_report.md`）。
- 新建简单结果表比较候选 writer 与现有 Direct OOXML 时，格式从简，但不得丢失字段/列序、文本代码、数值精度、公式、筛选、跳转等现有业务用途。
- 修改模板、回填反馈和跨工作簿复制单独验收，不能从“结果表样式要求少”推导出“模板无需保真”。新建 XLSX 的 writer 不承担既有文件编辑。
- 静态写入公式文本不等于计算公式；金额/阈值/舍入必须遵循现行契约，迁移不得把高精度 Decimal 静默缩减为低精度数值。

## S1 公式链路

- 分开评估公式解析与复制、OOXML 写入、Office 打开、重算、保存及结果提取；Rust 可优先优化计算前后的静态环节。
- 现行真实公式重算继续使用 Windows Excel/WPS 或 Linux LibreOffice。Rust 公式后端仅可先做隔离试验，完整兼容验收后才允许用于已覆盖的业务范围；未覆盖依赖仍交给 Office。
- 兼容性依据整个公式及其传递依赖，包括 INDIRECT 动态地址、INDEX 值/引用、命名区域、跨表/外部引用、辅助单元格、错误传播、共享/数组公式；单个函数“支持”不代表整本兼容。
- 修改输入与动态地址后重复验证重算和持久化缓存；禁止拿旧缓存、0 或空白代替未计算结果，也不得为提速擅改业务公式。具体文件边界见 `rules/03_Excel与OOXML边界.md`。

## 高级设置与失败处理

- 高级设置按系统、功能、操作分别提供读取/写入等工具选择，默认“自动”；只显示该操作已验收的后端，允许用户手动选择受支持的工具。
- 自动模式按能力和基准选择已验收的高效后端；回退只限明确的兼容失败，记录原因，并从干净输入/临时副本重新执行，禁止对部分写入的正式结果继续回退。
- 手动模式不得静默改用另一工具；不支持时说明对象、原因和可选处理方式。结果存在语义差异时先定位，不用回退掩盖差异。
- 运行记录保留有效后端及版本、路由/回退原因、阶段耗时；设置须持久化，迁移不清空现有选择。失败细节进入技术日志。

## 分开测试，再做完整验收

- 每个系统先固定当前实现、输入/配置及黄金结果，再分别测读取、计算、写入，最后测完整流程，保持原始业务文件只读。
- 读取对拍数据类型、值、空白/零/错误/缓存及行列位置；计算对拍取数、规则命中、级别、提示、失败/跳过语义；写入对拍单元格值、类型、公式和本功能要求的结构。
- 更换读取引擎前必须声明并统一 bool、日期、错误值的解释口径。基准中 Direct `CellValueProvider` 返回原始缓存值（bool 为 1/0、日期为序列号、错误值为缓存字符串），Calamine 返回解释后的 bool/datetime/error；未统一时不得切换默认读取引擎。依据：基准报告《读取一致性》及附录“type_error_edge_probe”。
- 跨语言读取对拍先归一空单元格记号：本次 `.xls` 侧测中 `python-calamine` 返回 `''`，Rust `calamine` 返回 `Empty`。归一前的摘要不一致不能直接判为数据错误；仍须保持业务空值语义。此观察限定于该侧测文件，其他格式须按各自适配器验收。依据：基准报告附录“real_xls_side_test”。
- 跨引擎浮点对拍不使用位精确 SHA-256 逐格摘要判等。数值比较使用相对容差不大于 `1e-15`，或将双方值按同一十进制规则归一后比较；摘要只用于同一引擎、同一序列化口径的前后对比。基准实际 S2 输出约 17,580 格中有 23 格相差 1 ULP。若业务契约要求位精确数值，差异未获业务验收前不得切换。依据：基准报告附录“实际 S2 写入：浮点末位（1 ULP）序列化差异”。
- `.xls` 扩展名但内容无有效 CFB/OLE 签名的文件（基准中有 HTML 伪装的 `.xls`）按格式不支持明确拒绝，作为预期输入拒绝单独统计，不计为引擎读取失败。依据：基准报告附录“real_xls_side_test”。
- 写入基准使用同一份预生成数据，不混入读取和计算；分别记录 Rust 内部耗时与包含跨语言转换的调用耗时，不能仅凭内部微基准宣称业务提速。Python↔Rust 子进程与 JSON 桥接的编码、数据复制/解码、进程启动、Rust 解析和保存/压缩耗时及峰值内存须单独计量，并纳入端到端结论。依据：基准报告《范围与实现审计》《写入阶段耗时中位数》。
- 在相同 ZIP 压缩级别下公平比较，再测各自交付设置并同时报告大小；同机同输入，预热后至少五次，记录中位数、波动、内存、规模和环境，不预先承诺提速倍数。
- XLSX 对拍以结构和业务语义为准，不以整个 ZIP 字节哈希相同为条件；输入执行前后哈希须不变。合并、样式、名称、宏、关系等按功能实际保留需求检查。
- 每完成一个系统，先跑其定向/系统组，再跑全项目 S1-S5 pytest 与 Windows/Linux AMD64 验证；新增测试登记 `core/tests/TEST_GROUPS.md`。未运行项目不得写成通过。
- Office 路径须在实际引擎上完成重算、保存和缓存验证，不能只用 mock；Windows 两种壳与 Linux 的适配/打包验收分别记录。
- 仅在结果无未解释差异、全量回归通过且性能收益稳定时切换默认；否则保留现行默认或已验收的手动备选，不强行替换。

## 平台与阶段交付

- Windows 与 Linux AMD64 分别构建原生扩展并验证加载；Linux 维持 glibc 2.28 兼容目标，暂不生成 ARM64 发布包。
- 核对保留目标的 Python ABI、位数及最低系统，尤其是旧 Windows/32 位/Python 3.8；固定兼容工具链和依赖版本，不能靠源码可编译推断目标机可运行。
- 每个系统交付功能差分、读取/计算/写入及总耗时对比、平台测试、有效路由和未执行项的带时间戳报告；真实数据/配置及报告仍遵守不入公开仓库的边界。
- 功能实施按 `rules/11` 版本留痕；只有本规范等治理文档变化时不升级产品/功能/配置版本，不向用户版更新日志加入开发过程。
